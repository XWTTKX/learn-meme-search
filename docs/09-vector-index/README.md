# 09 · 精确检索、Faiss与索引更新

## 先建精确基线，才能评估近似索引

对于归一化向量 $\lVert t-v\rVert^2=2-2t^Tv$，因此最大内积、最大余弦与最小欧氏距离给出同序排名。没有归一化时，内积会偏向范数大的图片。例：查询 $(1,0)$，图片 A 为 $(2,2)$，B 为 $(1,0)$。原始内积 A=2、B=1，余弦分别约 0.707 和 1，次序相反。把项目的归一化去掉再对照，能区分模型语义变化和度量设置错误。

先把图像向量和稳定 ID 一起存盘，精确内积作为参照。浮点 32 位、512 维、100 万张图，裸向量 $10^6\times512\times4=2.048$ GB，约 1.91 GiB；另计 ID、元数据、索引本身和灰度切换时的新旧两份。小库通常可以先用矩阵乘法或 Flat；数据量与延迟确实卡住后，再评估 HNSW 或 IVF。可参考 [Faiss 索引说明](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)。

| 方案 | 查询做的事 | 主要成本或失效点 |
|---|---|---|
| Flat | 对库中全部向量计算距离 | 查询成本随库大小线性增加 |
| HNSW | 从图入口逐层导航，在底层扩大候选搜索 | 图边占内存；调大搜索宽度通常增加延迟 |
| IVF | 先找若干最近簇，查对应桶中的候选 | 需要聚类训练；新数据分布变化时可能掉召回 |
| IVF-PQ | 在桶内基于量化码近似距离 | 压缩明显，精度受量化误差影响，可对多召回结果精排 |

## 两个 Recall 分开读

ANN Recall@K 比较近似 TopK 和精确 TopK 的交集。业务 Recall@K 比较系统 TopK 和人工正例。假设精确为 A、B、C，近似返回 B、C、D，ANN Recall@3 是 2/3；若唯一人工正例是 D，近似的业务 Recall 为 1，精确却为 0。这个例子说明业务指标并不能替代 ANN 校验。离线对照至少记录库大小、维度、参数、P50/P95、运行设备和冷/热启动，保持相同查询集和索引版本。

支持删除时，过滤发生在截断前后会改变有效 K。若 Top10 中 7 张已下架，取完再过滤只能返回 3 张。先扩大检索再过滤能缓解，但要报告过滤后的空结果与延时成本。严重时需要定期重建，并将模型、预处理、向量、ID 对照、过滤规则作为一个可回滚的版本包。

### 练习与答案

「上线后随机开一张图，向量排序却对应另一张图」先查什么？先拿单条已知图，测试查询向量与对应库向量的自相似度、索引行与 ID 的映射、以及图片版本的校验值。仅看 Top10 很像模型泛化失败，先隔离数据错位才不会在错误假设上微调模型。

先把精确检索作为正确性基准。图文向量均已归一化时，内积排序等价于余弦排序，也与欧氏距离排序等价；没有归一化时不能套用这个结论。

| 索引 | 优点 | 代价 | 起步建议 |
|---|---|---|---|
| Flat/IP | 精确、简单 | 每次遍历全库 | 小规模基线 |
| HNSW | 查询速度可调 | 图结构占内存，维护有成本 | 扩容实验 |
| IVF/PQ | 压缩大规模向量 | 聚类与量化误差，需要训练 | 有容量压力再做 |

ANN Recall@K 与任务 Recall@K不同：前者相对精确近邻结果，后者相对人工相关图片。ANN索引找到了模型认为最相似的图片，不代表找到了用户想要的图片。

实测记录模型版本、向量dtype、N/d、构建时间、查询P50/P95和ANN召回。查询至少包含足够不同文本，先预热，再区分编码耗时与向量检索耗时。

扩展任务：将可选脚本的逐图编码改成批量，并将向量缓存为不依赖pickle的数值数组，另存ID映射JSON。验证新增、替换、删除三种变更。本仓库未实现Faiss服务，不能把方案图当成部署成果。

参考：[Faiss官方索引选择指南](https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index)。
