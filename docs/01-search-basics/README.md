# 01 · 搜索系统基础：从一句话到候选集

## 一张图看懂「搜索」在做什么

```text
用户想表达：我今天很累
用户实际输入：累成狗
  ├─ 字面信号：累 / 成 / 狗          ──► 找带这些字的标签或 OCR
  └─ 语义信号：极度疲惫、可幽默回复   ──► 找姿态和表情像“累”的图
                    两路合并
                         │
                   相关、可用、少重复
                         ▼
                   让用户选一张发走
```

**先判你到底要找什么。** 如果用户输入「辛苦了」，可能要找可以发给别人表示慰劳的图，而不是找主角正在辛苦工作的图。将查询意图拆成「说话目的」和「画面要求」能降低歧义。要求可以分为硬条件与偏好：「一定要猫」是硬条件，「最好是 GIF」可能只是偏好。别把它们全塞给一个相似度，也别在没有证据时把某个场景定义成硬条件。

| 查询 | 硬条件或高置信线索 | 可以变化的部分 | 第一个坏例子 |
|---|---|---|---|
| 这班一天也上不下去 | 抱怨上班 | 人物、配文、静态或动图 | 「我爱上班」 |
| 叫我一声老板 | 若想找原图，逐字优先 | 同图的清晰度和尺寸 | 只有「老板」字样的招聘广告 |
| 震惊的猫 | 猫为主体且表现出震惊 | 猫的品种与画面背景 | 人震惊、角落有猫 |
| 量子纠缠示意动图 | 若图库完全没有，允许无结果 | 可以给相关查询建议 | 只因命中「图」就返回表情包 |

**什么时候值得增加一路召回？** 用三条样例观察「有没有找到」和「找到了排第几」。如果词法能检出全部正例，却把它们放太后，先改排序。若词法完全没有相关候选，再加图文、同义词或更完整的标签。把增益分到「新增候选」和「前移」两列，实验结论就能指导下一步。

## 先把请求翻译成可验收的需求

「搜索表情包」至少有三种不同目标：按台词找同一张图、按情绪找可以替代的图、按主体或画面找一类图。面对「我真的会谢」，文字相同也可能是感谢、反讽或吐槽。标注时先设定场景，否则两个标注者很可能各自都合理，却给出完全不同的标签。给查询加 intent 和可接受范围，例如「找可以回同事催稿的反讽表情，排除真诚感谢」。再选负例：普通鞠躬或带「谢谢」的公文截图虽然有词面匹配，却背离用途。

上线时能够接受的结果不仅由相关性决定。一屏多个结果时，要考虑同模板复刻是否占满位置；你可以定义一张包含不同模板的候选表，先找前几张相关图，再约束重复。现在先用六条样例确定检索与评价接口。待加入至少一条没有任何相关图的真实查询，再设计如何呈现空结果。

输入“不想上班”，用户需要的是能表达情绪的图片。检索对象是图片，但查询是文字，相关性既包含画面，也包含图中文字和社交语境。先把任务定义为 text-to-image retrieval，而不是生成图片或聊天机器人。

一次请求拆成：查询处理 → 候选召回 → 融合 → 排序 → 去重与展示。召回保证相关图片进入候选集；排序保证它们靠前。最终发送率属于线上目标，离线只能用人工相关性近似。微信真实搜索架构未在本仓库得到验证，这里是功能相似的个人项目。

## 三条容易混淆的路径

| 路径 | 输入与输出 | 适用查询 | 主要缺陷 |
|---|---|---|---|
| OCR/BM25 | 文字 → 图中文字 | “收到”“谢谢老板” | 无文字图片难匹配 |
| Chinese-CLIP | 文字向量 → 图片向量 | “猫咪震惊” | 否定、讽刺与梗语可能失败 |
| 标签检索 | 情绪/角色 → 元数据 | “无语 猫” | 人工标签覆盖有限 |

先选最简单、能被评测否定的基线。不要一开始堆向量库、消息队列和大模型。千张图用精确矩阵乘法通常足够作为起点，是否需要 ANN 由实测决定。

## 动手与验收

写 30 条查询，分为文字型、画面型、情绪型、否定型、组合型，每类至少 5 条。为每条写出“什么算相关”。验收时用同一图片解释：画面相似为何不一定符合表达意图？

面试追问：检索与分类有什么区别？答：检索要在不断变化的候选库上排序，分类通常在固定标签空间预测；两者的候选更新方式和评价指标不同。
