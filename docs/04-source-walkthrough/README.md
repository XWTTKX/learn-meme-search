## 4.1 先运行，得到需要解释的结果

想象用户刚开完会，在聊天里搜「疲惫」。图库里有两张能用：一个不想上班的打工人 m01，和一个开会想睡觉的人 m08。两张标签都包含完整的「疲惫」。它们应该同分吗？先猜，再在仓库根目录运行：

```bash
python3 scripts/trace_search.py '疲惫' --positive m01 --positive m08 --k 1
```

输出是一份可读的诊断 JSON。先只看最外层几个字段：

| 字段 | 实际结果（数字经四舍五入） | 用来回答 |
|---|---|---|
| `tokens` | `["疲","惫"]` | 输入被模型看成什么？ |
| `document_count` | 8 | 字频相对于多大的库？ |
| `average_length` | 6.625 | 长标签以什么参照判断？ |
| `query_df` | `{"疲":2,"惫":2}` | 这两个字各出现在几张图的标签里？ |
| `matching_docs` | m08：2.34304；m01：2.20599 | 都命中了，究竟差多少？ |
| `top_k` | `["m08"]` | 截到一个展示位时留下谁？ |
| `metrics` | Recall=.5，HitRate=1，MRR=1，NDCG=1 | 为什么会同时有半分和满分？ |

这里的 `--positive` 比模型得分晚使用：它不改变排名，只让你能对结果算指标。命令漏掉一个 `--positive`，评测就变成另一道题。若不传正例参数，`metrics` 为 `null`，表示未做标注对照。

这次先保留 m08 在前的事实，把问题记在纸上：**两个字命中次数完全相同，哪一个变量制造了不同分数？**

### 代码地图：这次读四个文件

```text
data/sample/memes.json               人手填写的标签，每条一个稳定 ID
        │
        ▼
scripts/trace_search.py              一条查询的观察窗口，不自己发明算法
        │
        ├─► scripts/retrieval.py      tokens → BM25 → 排序 → TopK
        │          │
        │          └── contributions()  列出每个字的分数贡献
        │
        └─► scripts/metrics.py        拿同一个 TopK 和人工正例计算指标

scripts/demo.py                      批测入口：同一个 BM25，另读固定查询集
```

`trace_search.py` 特意没有复制 BM25 公式，展示和排序都调用同一个 `contributions()`。如果用另一个手写公式生成解释，改了排序算法却忘记改解释，数值就会悄悄不一致。

## 4.2 把输入展开成三张表

先看 [样例 manifest](../../data/sample/memes.json)。这里只保存图片 ID、文字标签和图片路径。基线完全不打开图片路径；即便占位图片不存在，文字打分仍然可以进行。它的用途是教学，把分词、索引、排序和指标连起来。

### 4.2.1 分词保留了什么

[retrieval.py](../../scripts/retrieval.py) 的分词器：

```python
import re

def tokens(text):
    return re.findall(r"[\u4e00-\u9fff]|[a-z0-9]+", text.lower())

for sample in ("疲惫", "GIF 2026 😂", "不想上班！", "ＣＬＩＰ"):
    print(repr(sample), tokens(sample))
```

第一支正则每次匹配一个指定范围内的汉字；第二支把连在一起的小写 ASCII 字母和数字作为一个 token。空格与标点是天然分隔符。这份规则不会把表情符号当 token，也没有自动把全角字母变成半角。脚本里的 `lower()` 不等同于 Unicode 规范化。图文模型的 tokenizer 是另一条独立链路，不应假定跟这里切出来的一样。

输入 `疲疲疲惫` 先产生四个 token，打分前再按第一次出现的顺序去重成 `疲、惫`。这份教学版没有赋予重复输入的查询词额外权重。**文档侧重复出现依然增加 TF**，因此查询去重和文档去重不能混为一谈。

### 4.2.2 文档词频、文档长度和全库 DF

```text
m08："开会 困倦 疲惫 打工"  → [开 会 困 倦 疲 惫 打 工]   dl=8
m01："不想上班 打工人 疲惫" → [不 想 上 班 打 工 人 疲 惫] dl=9
查询："疲惫"  → [疲 惫]

相关字段：
                  m08 TF    m01 TF     全库 DF
       疲             1         1           2
       惫             1         1           2
```

源码的关键三句，用伪变量名拆开写如下：

```text
self.tf      = 每个文档各自的 Counter
self.lengths = 每个 Counter 的 value 之和
self.df      = 只遍历每个 Counter 的 key，再数各 key 出现了多少次
```

第三句是最常见的误读。若一篇描述写成「累累累」，它对 `TF(累,该文档)` 的贡献是 3，对 `DF(累)` 的贡献是 1。长度累加的是 token 次数，不是唯一 token 个数。一篇文档的 DF 拿不到；DF 始终是整个图库的统计量。

利用实际样例确认长度合计为 53，除以 8 得到平均长度 6.625。此平均值不是两条命中的平均长度，也不是只对包含查询字的图统计。添加不相关文档也可能改变已有图排序，因为它会改变 N、DF 的比例或平均长度。

### 4.2.3 为什么先读数据，而不是直接调参数

如果两个字都在 `query_df` 里是零，排查就该停在词法路输入与词表，不需要看长度惩罚。比如「累成狗」在本样例里词法为空；这与用 @1 还是 @10 无关。相反，「疲惫」两条都能命中，用 @1 只留一条就是排序和位置预算问题。把这两种失败写成同一个「Recall 低」，无法指导要改哪一层。

## 4.3 进入打分函数，手算并对照

### 4.3.1 先画一张函数内部图

```text
一个 token + 一篇文档
      │
      ├─ 文档 TF = 0 ─────► 没有贡献，不返回此项
      │
      └─ 文档 TF > 0
             ├── DF 与 N ─────────────► IDF
             └── TF、dl、avg、k1、b ──► TF 权重
                                          │
                               两个数相乘 ─┘
                                          ▼
                             与其他命中字的贡献相加
```

阅读 [contributions()](../../scripts/retrieval.py) 时，先找 `normalizer`，再找 `idf`，最后找到 yield。别试图盯着一行长公式全部记住；教学诊断将两项的中间值直接打印出来。

### 4.3.2 手算 m08 的「疲」

1. 在 8 篇文档中，「疲」的 DF=2，故 IDF=ln(1+6.5/2.5)=ln(3.6)≈1.28093。
2. m08 的长度比是 8/6.625≈1.20755。带入 b=.75 得到长度因子 .25+.75×1.20755≈1.15566。
3. 乘 k1=1.5 得分母额外的归一项约 1.73349。TF=1，所以 TF 权重为 2.5/(1+1.73349)≈0.91458。
4. 两项相乘：1.28093×0.91458≈1.17152。
5. 「惫」的 DF 和 TF 都相同，也是约 1.17152。总分约 2.34304。

m01 的第 2 步换为 9/6.625；其余数字不变。更长导致 TF 权重降到约 0.86109，每字贡献约 1.10300，总分是 2.20599。**本查询排序差只来自文档长度。** 对实际检索，这是一种默认偏好：同等命中下短标签更集中；它并不证明 m08 对每位用户都更好。

### 4.3.3 改一项参数，并预测名次

现在假设产品希望不同标注长度一视同仁。以长度因素为唯一变量试一次：

```bash
python3 scripts/trace_search.py '疲惫' --b 0 --positive m01 --positive m08 --k 1
```

当 b=0，`normalizer=k1`，在 TF=1 时两词权重都为 1。两篇文档得分同为 2×1.28093≈2.56187。最后的排序键是 `(-score, id)`，ID 更小的 m01 第一。**名次变了但相关性指标可能完全不变**，因为两张都是正例。单靠宏指标不能判断哪一个排序更符合用户对「开会」场景的偏好。

### 4.3.4 「打工」为何不应照抄「疲惫」的结论

换 query 后要重新读 `query_df` 并重新算 TF 与长度，不能说「短的永远靠前」。即使两篇都含「打工」，共有词的权重和其它可能含部分字符的文档也变了。查询「不想上班」中，标签只含「下班」的图仍可能靠共享的「班」被召回。看看 `matching_docs` 各条的 `parts`，会比只看一个总分更直观。

### 4.3.5 代码和运行成本的边界

当前实现先建 TF、DF、长度，再逐文档检查每个查询 token。若语料有 N 条、查询有 T 个唯一 token，逐文档判定约 O(NT)，还有候选排序。把每文档中间值保留并在 `trace_search.py` 打印，是用于排错的能力。在线大流量不应为每条 query 打印全部命中明细；可以只抽样保存，或通过倒排表把遍历范围收窄。倒排实验见 [第 08 章](../08-lexical-hybrid/README.md)。

## 4.4 为什么指标看起来彼此矛盾

```text
正例：m01、m08
Top1：m08
  找到 1 个 / 一共 2 个可选                → Recall = 0.5
  找到过至少一个                           → HitRate = 1
  首个正例在第 1 位                         → MRR = 1
  理想 Top1 也最多放 1 个正例，且都在第 1 位 → NDCG = 1
```

把 `--k 1` 改成 `--k 2` 后两个正例都能出现，Recall 变为 1。模型和分数没有改变，因此这种变化叫「展示位增加」，不是算法提效。现在再运行：

```bash
python3 scripts/demo.py --query '疲惫'
python3 scripts/demo.py --query '量子力学'
```

首行是你手输的一条 query，次行始终读取固定的 [查询样例文件](../../data/sample/queries.json)。只换 `--query` 并不会改变次行的汇总评测。汇总为满分只能说明人为构造的样例符合预期，不代表真实图片检索满分。想比较策略，要固定评价集、图库和 K，在同一条查询上记录差异。

## 4.5 换成图文路时，哪几个部分会变

词法路处理的是查询与文字标签；图片里的表情、手势和构图在后台不可见。可选入口 [clip_search.py](../../scripts/clip_search.py) 将图像和查询分别编码到同一个空间：

| 阶段 | 输入（假设三张图、隐向量 512 维） | 输出 | 检查问题 |
|---|---|---|---|
| 预处理 | 一张原始图片 | `[1,3,H,W]` | 是否 RGB？首帧是否足够表达动作？ |
| 图像编码 | 三次单图前向计算 | 三个 `[1,512]` | 形状、数据类型和归一化是否正确？ |
| 拼图库 | 三个规范化向量 | `[3,512]` | 第 i 行对应哪个图片 ID？ |
| 查询编码 | 一个字符串 | `[1,512]` | tokenizer 和模型是否是配套版本？ |
| 计算内积 | `q @ bank.T` | `[1,3]` | 索引行号是否还和 manifest 对应？ |

返回的是排名分数，归一化后可按余弦解释，不是用户喜欢的概率。如果模型变了，向量需重算；如果只有 ID 命中的图片显示错了，先查行号到 ID 的映射。这个入口的开发形态每次查询都重算全部图片，不把它当作已优化的在线检索。

上游读法：用 [来源表](../../SOURCES.md) 固定版本，先看 Chinese-CLIP 的双塔与推理示例，再看训练中的双向损失；独立对照 StickerSearch 模型加载、索引构建与查询响应这三段。只研究实现结构，不将上游指标说成这个项目实测。图文公式见 [第 05 章](../05-clip-learning/README.md)。

## 4.6 排错和课后练习

| 观察 | 先查哪一步 | 可执行的验证 |
|---|---|---|
| 生僻输入没有返回 | token 与 DF | 打印 token，词项是否全不在词表 |
| 有结果却全不相关 | 命中项的颗粒度 | 逐项查 `parts`，是否「力」一字触发 |
| 指标低但全部正例在 matching_docs | TopK 或排序 | 固定 K，对比正例位置与得分 |
| 调数据后汇总异常 | 标签 ID | 正例是否仍是当前 manifest 内有效 ID |
| 换模型后显示错图 | 图向量与 ID 对照 | 用同图片自相似和稳定 ID 做最小检查 |

<details>
<summary>练习一：查询改成「疲疲疲惫」，预测输出</summary>

当前实现按第一次出现的顺序去重为同样的两个字，因此排名和贡献明细等未变，query 字段不同。对文档里的「疲」加三次则不同，因为 TF 与全局平均文档长度都变了。
</details>

<details>
<summary>练习二：如何区分「命中了但未展示」与「压根没有命中」？</summary>

检查正例是否在 matching_docs 中。比如 K=1 时 m01 在 matching_docs、不在 top_k：排序/展示截断；对「累成狗」，两张都没进 matching_docs：词法召回缺信号。修复方法也不同。
</details>

<details>
<summary>练习三：图像路径全部写错，程序为什么还能跑？</summary>

标准库 BM25 不读取图片内容，结果不受路径影响。你可以复制一份 manifest 改路径再验证；不要直接改仓库样例。要验证像素路径，请用有权使用的本地图像在可选推理中看单图能否编码。
</details>

**面试复述。** 我用同一条「疲惫」请求打印每个字的 IDF 和权重，发现 m08 更靠前来自长度归一化，不是语义更好。把 b 改成零后两篇同分，稳定 ID 决定顺序。这个实验让我能区分统计项、排序规则和评价指标各解释什么。
