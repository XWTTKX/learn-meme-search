# 16 · 90秒介绍与项目深挖

## 把失败展开成一段能追问的故事

任务：我要支持短句搜表情，但文字与图片表达常不一致。动作：先用字符 BM25 建可跑基线，挑选台词、语义、无答案三类样例；然后设计 RRF，以两个显式的候选列表验证排序变化。结果：代码层面，我能重现语义正例只来自图文路的案例，也发现无答案仍可能被「力」这种单字误召回；这只是教学案例，没有实际线上收益。下一步：收集有授权图库的人工标签，比较按词拆分、二元组、阈值和图文融合。

追问如何应对：「那你怎么讲自己排查最多的一次？」具体指定一条 query、一行中间数据、一处修复、一项不会回归的验收。切忌把问题描述成「召回不好所以用了更先进的模型」；用「哪些正例本来就不在候选」「哪些只是排名落后」给出不同抓手。

## 90秒项目介绍模板

背景：本地表情包多，按文件名难找。目标：给自然语言查询返回表达相应情绪的图片。方法：先建文字检索基线，再尝试Chinese-CLIP图文召回，通过RRF融合。验证：按查询意图构建独立标注集，用Recall/NDCG和分桶错误分析比较。结果：仅填自己跑出的数字；还没实测就说明当前实现和下一步。

## STAR只用于真实发生的经历

- S：记录一个具体失败，如“文字相关但画面反义”。
- T：定义要改善的查询子集和不能明显退化的指标。
- A：描述你定位、假设、实现和消融的过程。
- R：报告观察到的结果，包括退化或无提升，以及下一步。

## 追问链

“为什么不用大模型生成描述？”→ 描述可以增加可检索文字，但有离线成本和幻觉，需要比较真实提升。

“你做的最难部分？”→ 从真实经历选数据标注、语义假负例或索引一致性，给一个具体错误和修复证据。

“再给一周会做什么？”→ 基于当前失败分布选一个改进；例如否定查询多则先做标注与结构化过滤，不凭热点换模型。

验收：录音两分钟，删掉不能给证据的形容词；让同学连续问五个“为什么”。
