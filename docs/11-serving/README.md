# 11 · 服务化、延迟与可观测性

## 将故障映射到可观察的量

词法 8ms、向量 60ms、融合和过滤 9ms，若并行执行，两路耗时约取最慢分支而不是相加，整体还要算排队、编码、序列化和网络。向量路超时可先返回词法候选，但是情绪 query 空结果会升高。至少记录总 P95 / P99、各路超时率、过滤后结果数和各路实际入选率。失败请求和降级请求要纳入统计；只在成功的向量请求上算延迟会漏掉用户遇到的慢请求。

分诊例：索引更新后空结果上升，但两路候选数没降。检查过滤规则、候选 ID 是否能查到元数据、结果去重比例。若索引和图片可见列表错版本，模型分数再高也没用。服务降级后不要把不同策略同键缓存，否则回到健康状态仍会看到缺少向量候选的旧结果。可在固定测试环境人工模拟向量超时，核对可返回词法结果并报告清晰的降级原因。

完成离线评测后再包装服务。一个最小搜索API可以接受 `query,top_k,index_version`，返回 `image_id,rank,route,latency_ms`。路径访问限制在指定图库目录，不把任意文件读取功能暴露到外部。

延迟拆成：预处理、文本编码、召回、融合、组装。冷启动模型加载和热请求延迟分别统计。P95需要足够请求，十条查询不足以得出稳定服务结论。并发吞吐测试必须同时记录硬件与批量策略。

缓存键至少包含规范化查询、模型版本、索引版本和过滤条件。只按文本缓存可能在用户切换图库后泄漏或返回旧结果。用户私有图库必须隔离候选池。

## 降级顺序

图文模型不可用时可回退文字通道；图片缺失时跳过并记录；索引维度不匹配时拒绝加载；新版本健康检查失败时保留旧版。不能用空结果掩盖全部服务故障。

此章是工程扩展设计，交付脚本是本地CLI。验收产物应包括API样例、一次模型加载失败的演练和完整压测命令。没有真正运行API前，不在简历写QPS。
